Clase 0 — Instalación y primer PASS

Objetivo: ver ✓ PASS en un escenario real que ya escribí.

Necesitas: Node.js 18+, una terminal, unos quince minutos.

npm install -g @natl/cli @natl/adapter-playwright
npx playwright install chromium
natl --version

Clona el repo y ejecuta el fixture de login (HTML local — sin sitio público inestable):

git clone https://github.com/arslan-ahmetjanov/natl.git
cd natl/examples
natl run login.yaml

¿Esa sensación cuando pasa? Consérvala. Todo lo demás en este curso es más de eso.

Prueba esto: rompe el texto del assert a propósito, vuelve a ejecutar, lee la línea FAIL (archivo + paso). Arréglalo. El aprendizaje empieza cuando rompes cosas con seguridad.

Clase 1 — Anatomía de un escenario

Abre examples/login.yaml conmigo:

name: Login smoke
engine: playwright
tags: [smoke]
vars:
  base_url: ./fixtures/shop.html
  user: demo@test.com
  pass: secret
steps:
  - goto: $base_url
  - fill: "#email"
    with: $user
  - fill: "#password"
    with: $pass
  - click: "#login-btn"
  - assert: ".welcome"
    text: "Добро пожаловать"

De arriba a abajo:

  • name — lo que ves en el reporte
  • engine — cómo manejamos el navegador (playwright por defecto; también selenium, cypress o http)
  • tags — etiquetas opcionales para --tags
  • vars — valores que referencias como $user
  • steps — el script

Otros campos raíz que verás pronto: timeout, retries, secrets, imports, cases, before_each / after_each, elements, actions, locator_strategy, data. Lista completa → Sintaxis.

Prepara tu propio proyecto cuando quieras dejar mis fixtures:

mkdir my-tests && cd my-tests
natl init
natl run tests/

Clase 2 — Pasos UI y asserts

Diseñé los verbos para que un smoke quepa en una pantalla. Ritmo principal: objetivo + comprobación.

- goto: $base_url
- fill: "#email"
  with: $user
- select: "#country"
  with: "KZ"
- check: "#agree"
- click: "#submit"          # tap: is the same step
- assert: ".ok"
  text: "Done"
- assert: ".ok"
  contains: "Do"
- assert: ".banner"
  visible: true
- assert: ".banner"
  attr: class contains "active"
- assert: current_url contains "/dashboard"

Auto-wait: acciones y asserts esperan el objetivo dentro de timeout. Normalmente no necesitas wait: ".ok visible" antes de un assert.

Usa wait: explícito para retrasos (wait: 500), hidden / attached / detached, o tiempos poco habituales.

Fallos suaves (recopilar, no parar):

- assert: ".price"
  text: "$10"
  soft: true
# alias:
- soft_assert: ".stock"
  visible: true

Captura y extrae cuando necesites un valor después:

- get_text: ".title"
  save: page_title
- get_attr: "#link"
  attr: href
  save: href
- screenshot:
    file: artifacts/after-login.png
    full_page: true
- set: $total = $price * $qty
- log: "total=$total"

Gestos (el mismo escenario para web de escritorio y móvil — sin if: mobile):

- scroll: "#footer"
  into_view: true
- swipe: "#carousel"
  direction: left
- long_press: "#card"
  duration_ms: 700

Prueba esto: ejecuta examples/soft_assert_demo.yaml y examples/gestures_demo.yaml.

Clase 3 — Vars, secrets y config del proyecto

$name viene de vars (y de filas de case, includes, llamadas POM). Anidado: $order.id.

Secrets desde el entorno — nunca subas contraseñas reales:

secrets:
  env:
    file: .env

vars:
  user: $env.TEST_USER
  pass: $secret.TEST_PASS

$env.KEY y $secret.KEY leen el mismo almacén; los secrets se enmascaran en logs. Ver examples/env_login.yaml.

Los defaults del proyecto viven en natl.config.yaml:

engine: playwright
browser: chromium
timeout: 15000
base_url: https://staging.example.com
headless: true
artifacts_dir: artifacts
retries: 0
trace: on-fail
video: off

Entornos sin copiar URLs en cada archivo:

config/staging.yaml
config/prod.yaml

natl run tests/ --env staging
natl run tests/ --config config/prod.yaml

Orden de merge (gana el más alto): flags CLI → YAML del test → perfil env → natl.config → defaults.

Clase 4 — Page objects (do:)

Pon selectores y flujos con nombre en un archivo de página. Llámalos desde el escenario.

# pages/login.yaml
elements:
  email: "#email"
  password: "#password"
  submit: "#login-btn"
actions:
  login:
    - fill: $email
      with: $user
    - fill: $password
      with: $pass
    - click: $submit

# pom_login.yaml
imports:
  - pages/login.yaml
steps:
  - goto: $base_url
  - do: login.login
    user: $user
    pass: $pass

do: page.action es el camino feliz. include: login/login es la forma de más bajo nivel (archivo o reutilización de archivo entero). Las claves hermanas en do: se fusionan en el scope de la action.

La estrategia de locator vive en config / page / element — no en cada paso. Web hoy: css, xpath.

elements:
  title:
    strategy: xpath
    value: "//h1"

Prueba esto: natl run pom_login.yaml desde examples/.

Clase 5 — Data-driven cases:

Un escenario, muchas filas. Cada fila se fusiona en vars y ejecuta steps una vez.

name: Data-driven login
cases:
  - { name: user1, user: "a@test.com", pass: secret, expect: "Welcome, A" }
  - { name: user2, user: "b@test.com", pass: secret, expect: "Welcome, B" }
steps:
  - goto: $base_url
  - fill: "#email"
    with: $user
  - fill: "#password"
    with: $pass
  - click: "#login-btn"
  - assert: ".welcome"
    text: $expect

Los nombres en el reporte se ven como Data-driven login [user1]. Usa name o label en la fila; si no, [case N].

Para bucles anidados o calculados, usa data: + for: (siguiente clase). Prefiere cases: para tablas simples.

Prueba esto: natl run data_driven.yaml.

Clase 6 — HTTP y with: http

Escenario solo API:

engine: http
vars:
  base_url: http://127.0.0.1:8765
steps:
  - get: $base_url/get
    save: ping
  - post: $base_url/post
    body: { hello: world }
    headers: { X-Test: "1" }
    save: echo
  - assert: $echo.status == 200
  - assert: $echo.ok == true

Verbos: get / post / put / patch / delete. Valor guardado: { status, headers, body, ok }. El legacy api: sigue funcionando — prefiere los verbos.

UI + API en un archivo — cambia contexto con un bloque (no un engine: por paso):

engine: playwright
steps:
  - goto: $base_url
  - with: http
    steps:
      - get: $api_base/get
        save: ping
      - assert: $ping.status == 200
  - click: "#refresh"

Mis demos HTTP necesitan el stub local primero:

node stubs/echo-server.mjs
# other terminal:
natl run http_only.yaml
natl run ui_http_block.yaml

Clase 7 — Flujo: if / for / repeat / parallel

- if: $role == "admin"
  then:
    - click: "#admin"
  else:
    - click: "#user"

- for: $item in $data
  steps:
    - log: $item.name

- for: $i in range(1, 3)
  steps:
    - log: "i=$i"

- repeat: 3
  steps:
    - click: "#next"   # sets $i each time

- repeat:
    until: $done == true
  steps:
    - click: "#poll"

- parallel:
    - get: $api/a
      save: a
    - get: $api/b
      save: b

before_each / after_each se ejecutan alrededor de steps en cada intento (incluidos retries).

Expresiones: == != > < >= <= contains matches and or not. Builtins incluyen now, today, random_*, len, trim, upper, lower, range, y más — ver Sintaxis → Expresiones.

Clase 8 — Tags, retries y filtros CLI

name: Checkout
tags: [smoke, checkout]
retries: 1
natl run tests/ --tags smoke
natl run tests/ --tags smoke,auth
natl run tests/ --grep "Login"
natl run tests/ --retries 2
natl run suite.yaml --engine selenium
natl run suite.yaml --headed

--tags es OR. Combinado con --grep → AND. Cero coincidencias → exit 1.

Los retries vuelven a ejecutar el escenario entero con un contexto de navegador nuevo. Gana el último intento; el JSON puede marcar flaky: true.

Problem set

  1. Desde examples/, pon en verde login.yaml, pom_login.yaml y data_driven.yaml.
  2. natl init en una carpeta nueva. Apunta base_url a una página que te importe. Escribe un smoke de tres pasos.
  3. Extrae selectores a pages/ y llámalos con do:.
  4. Añade un bloque with: http que compruebe un endpoint de health (usa el echo stub si lo necesitas).
  5. Etiquétalo smoke y ejecuta con --tags smoke.

Si te atasacas — Troubleshooting. Si necesitas cada campo — Sintaxis.
