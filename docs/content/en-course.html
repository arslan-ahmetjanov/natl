Lecture 0 — Setup & first PASS

Goal: see ✓ PASS on a real scenario I already wrote.

You need: Node.js 18+, a terminal, about fifteen minutes.

npm install -g @natl/cli @natl/adapter-playwright
npx playwright install chromium
natl --version

Clone the repo and run the login fixture (local HTML — no flaky public site):

git clone https://github.com/arslan-ahmetjanov/natl.git
cd natl/examples
natl run login.yaml

That feeling when it passes? Keep it. Everything else in this course is more of that.

Try this: break the assert text on purpose, run again, read the FAIL line (file + step). Fix it. Learning starts when you break things safely.

Lecture 1 — Anatomy of a scenario

Open examples/login.yaml with me:

name: Login smoke
engine: playwright
tags: [smoke]
vars:
  base_url: ./fixtures/shop.html
  user: demo@test.com
  pass: secret
steps:
  - goto: $base_url
  - fill: "#email"
    with: $user
  - fill: "#password"
    with: $pass
  - click: "#login-btn"
  - assert: ".welcome"
    text: "Добро пожаловать"

Top to bottom:

  • name — what you see in the report
  • engine — how we drive the browser (playwright by default; also selenium, cypress, or http)
  • tags — optional labels for --tags
  • vars — values you reference as $user
  • steps — the script

Other root fields you'll meet soon: timeout, retries, secrets, imports, cases, before_each / after_each, elements, actions, locator_strategy, data. Full list → Syntax.

Scaffold your own project when you're ready to leave my fixtures:

mkdir my-tests && cd my-tests
natl init
natl run tests/

Lecture 2 — UI steps & asserts

I designed the verbs so a smoke fits on one screen. Primary rhythm: target + check.

- goto: $base_url
- fill: "#email"
  with: $user
- select: "#country"
  with: "KZ"
- check: "#agree"
- click: "#submit"          # tap: is the same step
- assert: ".ok"
  text: "Done"
- assert: ".ok"
  contains: "Do"
- assert: ".banner"
  visible: true
- assert: ".banner"
  attr: class contains "active"
- assert: current_url contains "/dashboard"

Auto-wait: actions and asserts wait for the target within timeout. You usually do not need wait: ".ok visible" before an assert.

Keep explicit wait: for delays (wait: 500), hidden / attached / detached, or unusual timing.

Soft failures (collect, don't stop):

- assert: ".price"
  text: "$10"
  soft: true
# alias:
- soft_assert: ".stock"
  visible: true

Capture & extract when you need a value later:

- get_text: ".title"
  save: page_title
- get_attr: "#link"
  attr: href
  save: href
- screenshot:
    file: artifacts/after-login.png
    full_page: true
- set: $total = $price * $qty
- log: "total=$total"

Gestures (same scenario for desktop and mobile web — no if: mobile):

- scroll: "#footer"
  into_view: true
- swipe: "#carousel"
  direction: left
- long_press: "#card"
  duration_ms: 700

Try this: run examples/soft_assert_demo.yaml and examples/gestures_demo.yaml.

Lecture 3 — Vars, secrets, project config

$name comes from vars (and from case rows, includes, POM calls). Nested: $order.id.

Secrets from the environment — never commit real passwords:

secrets:
  env:
    file: .env

vars:
  user: $env.TEST_USER
  pass: $secret.TEST_PASS

$env.KEY and $secret.KEY read the same store; secrets are masked in logs. See examples/env_login.yaml.

Project defaults live in natl.config.yaml:

engine: playwright
browser: chromium
timeout: 15000
base_url: https://staging.example.com
headless: true
artifacts_dir: artifacts
retries: 0
trace: on-fail
video: off

Stands without copying URLs into every file:

config/staging.yaml
config/prod.yaml

natl run tests/ --env staging
natl run tests/ --config config/prod.yaml

Merge order (highest wins): CLI flags → test YAML → env profile → natl.config → defaults.

Lecture 4 — Page objects (do:)

Put selectors and named flows in a page file. Call them from the scenario.

# pages/login.yaml
elements:
  email: "#email"
  password: "#password"
  submit: "#login-btn"
actions:
  login:
    - fill: $email
      with: $user
    - fill: $password
      with: $pass
    - click: $submit

# pom_login.yaml
imports:
  - pages/login.yaml
steps:
  - goto: $base_url
  - do: login.login
    user: $user
    pass: $pass

do: page.action is the happy path. include: login/login is the lower-level form (file or whole-file reuse). Sibling keys on do: merge into the action scope.

Locator strategy lives on config / page / element — not on every step. Web today: css, xpath.

elements:
  title:
    strategy: xpath
    value: "//h1"

Try this: natl run pom_login.yaml from examples/.

Lecture 5 — Data-driven cases:

One scenario, many rows. Each row merges into vars and runs steps once.

name: Data-driven login
cases:
  - { name: user1, user: "a@test.com", pass: secret, expect: "Welcome, A" }
  - { name: user2, user: "b@test.com", pass: secret, expect: "Welcome, B" }
steps:
  - goto: $base_url
  - fill: "#email"
    with: $user
  - fill: "#password"
    with: $pass
  - click: "#login-btn"
  - assert: ".welcome"
    text: $expect

Report names look like Data-driven login [user1]. Use name or label on the row; otherwise [case N].

For nested or computed loops, use data: + for: (next lecture). Prefer cases: for simple tables.

Try this: natl run data_driven.yaml.

Lecture 6 — HTTP & with: http

API-only scenario:

engine: http
vars:
  base_url: http://127.0.0.1:8765
steps:
  - get: $base_url/get
    save: ping
  - post: $base_url/post
    body: { hello: world }
    headers: { X-Test: "1" }
    save: echo
  - assert: $echo.status == 200
  - assert: $echo.ok == true

Verbs: get / post / put / patch / delete. Saved value: { status, headers, body, ok }. Legacy api: still works — prefer the verbs.

UI + API in one file — switch context with a block (not a per-step engine:):

engine: playwright
steps:
  - goto: $base_url
  - with: http
    steps:
      - get: $api_base/get
        save: ping
      - assert: $ping.status == 200
  - click: "#refresh"

My HTTP demos need the local stub first:

node stubs/echo-server.mjs
# other terminal:
natl run http_only.yaml
natl run ui_http_block.yaml

Lecture 7 — Flow: if / for / repeat / parallel

- if: $role == "admin"
  then:
    - click: "#admin"
  else:
    - click: "#user"

- for: $item in $data
  steps:
    - log: $item.name

- for: $i in range(1, 3)
  steps:
    - log: "i=$i"

- repeat: 3
  steps:
    - click: "#next"   # sets $i each time

- repeat:
    until: $done == true
  steps:
    - click: "#poll"

- parallel:
    - get: $api/a
      save: a
    - get: $api/b
      save: b

before_each / after_each run around steps on every attempt (including retries).

Expressions: == != > < >= <= contains matches and or not. Builtins include now, today, random_*, len, trim, upper, lower, range, and more — see Syntax → Expressions.

Lecture 8 — Tags, retries, CLI filters

name: Checkout
tags: [smoke, checkout]
retries: 1
natl run tests/ --tags smoke
natl run tests/ --tags smoke,auth
natl run tests/ --grep "Login"
natl run tests/ --retries 2
natl run suite.yaml --engine selenium
natl run suite.yaml --headed

--tags is OR. Combined with --grep → AND. Zero matches → exit 1.

Retries re-run the whole scenario with a fresh browser context. Last attempt wins; JSON may mark flaky: true.

Problem set

  1. From examples/, get login.yaml, pom_login.yaml, and data_driven.yaml green.
  2. natl init a new folder. Point base_url at a page you care about. Write a three-step smoke.
  3. Extract selectors into pages/ and call them with do:.
  4. Add a with: http block that checks a health endpoint (use the echo stub if you need one).
  5. Tag it smoke and run with --tags smoke.

When you're stuck — Troubleshooting. When you need every field — Syntax.
